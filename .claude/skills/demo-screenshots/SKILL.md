# Screenshots

Every image in `docs/images` is generated by `scripts/screenshots.mjs` against
the running application. No image is ever taken by hand: a hand-made picture
drifts from the app within a week, and a reader cannot reproduce it.

## Running it

```bash
cd cap && npm start            # one terminal
cd cap && npm run screenshots  # another; add names to limit: -- cockpit inbox
```

It drives the installed Chrome headless through `puppeteer-core` (no Chromium
download). `CHROME_PATH` overrides the browser, `DEMO_URL` the address.

## Adding an image

Add a `shot(...)` call. The options carry the whole state of the picture:

- `user` - the demo user; it is written as the `acme-demo-user` cookie, which
  is also how the app itself switches users. Basic auth is only a fallback.
- `language` (`de`/`en`), `theme` (`sap_horizon`/`sap_horizon_dark`)
- `tour: true` to show the onboarding tour, `script: true` for the demo drawer;
  both are otherwise suppressed, because a tour popup in a README image hides
  the screen it is explaining
- `after` - a function to scroll somewhere or open a menu before the shutter
- `wait` - Fiori Elements needs ~5 s before a list report is populated; a
  screenshot taken too early shows the loading skeleton

Every shot runs in its own browser context, because Chrome keeps basic
credentials per context - without that, every image shows the first user.

## After generating

Look at the images before committing them (`Read` shows them). Check for: the
loading skeleton, a tooltip left open by a focused button, a cut-off column, a
German text in an English screenshot. Then reference them from the README with
a caption that says what the picture proves, not what it shows.
